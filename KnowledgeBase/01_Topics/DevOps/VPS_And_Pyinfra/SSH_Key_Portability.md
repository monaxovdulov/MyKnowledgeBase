# Переносимость SSH-доступа между машинами

> Карта трека: [[VPS_And_Pyinfra_MOC]]

Задача: твой SSH-доступ к серверам не должен умирать вместе с конкретной
Windows. Разбираем по слоям — **что путешествует** (приватный ключ), **что
запускаем** (код бутстрапа) и **как вообще избежать задачи** (ключ при
создании сервера).

## Вариант 0 — ключ при создании сервера (лучший)

Большинство VPS-провайдеров при заказе сервера дают поле «SSH-ключ»: вставляешь
свой pubkey → `authorized_keys` появляется на сервере с рождения, и весь этап
копирования ключа **отпадает вовсе**. При заказе следующего сервера у aeza
проверить наличие этого поля — если есть, шаг «положить pubkey» не нужен.

## Вариант 1 — менеджер паролей как перенос ключа

Ключ хранится в зашифрованном хранилище, которое синхронизируется — на новой
машине ставишь менеджер, вводишь мастер-пароль, ключ доступен.

### KeePassXC + SSH Agent

- Ключ кладётся **вложением** в запись БД; KeePassXC умеет быть SSH-агентом
  (поддерживает Windows OpenSSH и PuTTY Pageant) — ключ отдаётся ssh без
  распаковки на диск.
- Перенос = файл `.kdbx`, синхронизируемый как угодно (Яндекс.Диск, флешка).
- На новой винде: KeePassXC → открыть базу → включить SSH Agent в настройках →
  `ssh-add -l` показывает ключ. Настройка агента включается на каждой машине.

### Bitwarden SSH Agent (десктоп ≥ 2025.1.2)

- SSH key — отдельный тип записи в хранилище; импорт из буфера
  (`-----BEGIN OPENSSH PRIVATE KEY-----`, форматы OpenSSH/PKCS#8).
- Десктоп-приложение поднимает локальный сокет (`SSH_AUTH_SOCK`) — ssh, git и
  прочие ходят за подписью в Bitwarden вместо системного агента.
- Синхронизация самим Bitwarden'ом — самый «нулевой» перенос.
- Ограничения: не работает в Linux Flatpak и macOS-сборке из App Store.

### 1Password

Платный, но эталонный SSH-агент (генерация ключей, биометрия, синк на все
устройства, git-подпись). Если уже платишь — использовать его.

## Вариант 2 — аппаратный ключ (максимум переносимости и безопасности)

FIDO2-токен (YubiKey и др., firmware 5.2.3+): приватный ключ физически не
покидает устройство — переносить нечего, носишь токен.

```powershell
ssh-keygen -t ed25519-sk -O resident -O verify-required -C "devuser-anywhere"
```

- `resident` — credential живёт на токене; на любой новой машине восстановление
  handle-файла: `ssh-keygen -K`.
- `verify-required` — PIN (или биометрия на Bio) при каждом использовании.
- OpenSSH на клиенте ≥ 8.3 для `ssh-keygen -K`.
- **Обязательно резервный токен**: вторая строка в `authorized_keys` под второй
  ключ, лежит отдельно; при потере токена строку сразу удаляем.
- Прагматика: украденный файл ключа бесполезен уже сейчас (passphrase), токен
  добавляет «физическое наличие» — следующий уровень, когда захочется.

## Что путешествует в git — код, не ключи

- `vps-config` репозиторий (инвентарь + `bootstrap.py` + `files/`): на любой
  машине `git clone` → `pyinfra bootstrap_inv.py bootstrap.py
  --ssh-password-prompt` — бутстрап переносим по определению
  ([[08_Bootstrap_Second_Server]]). Приватных ключей там нет и быть не может.
- `~/.ssh/config` (алиасы `vps`) — только имена хостов, секретов нет: можно
  держать в личном dotfiles-репо.

## Антипаттерны

- Приватный ключ в git / открытым файлом в облаке / в Telegram «избранное» /
  почтой. Утечка файла без passphrase = чужой вход на сервер.
- pubkey в репо — можно, это публичная часть (так и делаем в `files/`).

## Выбор для нашего сетапа

3. Новый сервер у провайдера: сначала ищем поле «SSH-ключ» при заказе.
