# Модель пользователей на сервере

> Карта трека: [[VPS_And_Pyinfra_MOC]] · Дополнительная заметка (вне порядка шагов)

Кто под кем работает на сервере и зачем делить пользователей.

## Три роли

| Пользователь | Зачем | SSH-вход | sudo |
|---|---|---|---|
| `devuser` | ты + агенты/инструменты разработки: администрирование, деплой, кодинг | да, по ключу | да |
| `srv-<app>` (`srv-swapp`, `srv-bot`…) | запуск публичного приложения/бота | нет | нет |
| `root` | только через `sudo` у devuser | нет (шаг 3) | — |

Агент, который кодит на сервере (AI-ассистент, CI-раннер), работает **под devuser**, как ты: ему нужны git, тесты, `docker compose`. Рабочие каталоги — в `/home/devuser/ai-projects/`. Чтобы агент без присмотра не упирался в запрос sudo-пароля, devuser добавляется в группу `docker`:

```bash
sudo usermod -aG docker devuser   # после установки Docker; docker-группа ≈ root, это принятый компромисс для dev-пользователя
```

Отдельный пользователь `agent` без sudo имеет смысл только если хочется жёстко оградить агента — но с доступом к docker выигрыш небольшой, а настройки больше.

## Почему приложение не запускать под devuser/root

Принцип наименьших прав: если приложение скомпрометируют, у злоумышленника должно быть минимум — только файлы этого приложения. Под `devuser` он получил бы твою домашнюю папку, SSH-ключи и sudo; под root — вообще всё.

## Сервисный пользователь

```bash
# системный пользователь без логина и пароля
sudo useradd --system --shell /usr/sbin/nologin --home-dir /opt/srv-swapp srv-swapp
sudo mkdir -p /opt/srv-swapp && sudo chown srv-swapp:srv-swapp /opt/srv-swapp
```

`--shell /usr/sbin/nologin` — вход невозможен даже с паролем. Переключиться под него для обслуживания: `sudo -u srv-swapp -s` или `sudo -iu srv-swapp`.

## Если приложения в Docker

Контейнер уже изолирует процесс — тогда сервисный пользователь нужен в основном чтобы **владеть файлами на хосте** (код, bind-mount volumes, `.env`). Практичный минимум:

- файлы приложения принадлежат его сервисному пользователю;
- внутри контейнера процесс тоже не под root (`USER` в Dockerfile);
- сервисных пользователей **не** добавлять в группу `docker` — член этой группы ≈ root на хосте;
- запускать `docker compose` может твой `devuser` через sudo или членство в `docker` (для личного VPS приемлемо).

## Сколько сервисных пользователей

- Публичное приложение, торчащее в интернет → свой пользователь.
- Несколько внутренних скриптов/ботов без внешней поверхности → допустим общий `srv-apps`, но разделять всё же лучше.
